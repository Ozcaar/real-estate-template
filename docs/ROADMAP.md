# Roadmap

This document summarizes the current implementation state of the Real Estate Website Template, the active task, and the upcoming sequence. It is the canonical entry point for resuming work in a new OpenCode session.

For architecture, theming, data models, i18n rules, and component conventions, see the topic-specific docs in `docs/`. For per-implementation details and the rationale behind individual decisions, see the JSDoc on the corresponding source file. This file is intentionally short and summarises state; it does not duplicate larger docs.

## 1. Project Purpose

A modular, configuration-driven real estate website template that can be rebranded to any agency without editing components. Public site only for the MVP — properties, developments, agents, contact, and lead capture UI over static data. See `docs/SPEC.md` and `docs/REBRANDING.md` for the full scope and the rebrand workflow.

## 7. Important Architectural Decisions

These are the decisions a new session needs to know to avoid re-litigating them. Each is enforced by the codebase; do not undo them without updating the relevant `docs/` file.

* **Nuxt 4 feature-first architecture** under `app/features/<domain>/{api,components,composables,constants,data,schemas,services,stores,types,utils}/`. Shared infrastructure lives under `app/components/{ui,layout,shared}/`, `app/core/`, `app/config/`, `app/themes/`, and `app/composables/`. See `docs/ARCHITECTURE.md` and `AGENTS.md` "Architecture".
* **Agency branding is configuration-driven.** All agency identity, contact details, social links, currency, measurement unit, and enabled modules live in `app/config/agencies/*.agency.ts` and are read through `useSiteConfig()`. Components never hardcode agency content. See `docs/REBRANDING.md`.
* **Theme tokens are CSS variables, not Tailwind palette classes.** The active theme is resolved by `app/themes/index.ts` and serialized into `var(--color-*)`, `var(--radius-*)`, `var(--shadow-*)`, `var(--font-*)` on `<html data-theme="…">`. Components use the variables; Tailwind color utilities are not used for brand colors.
* **i18n keys everywhere.** No hardcoded visible UI text. Every `$t('key')` is defined in both `i18n/locales/en.json` and `i18n/locales/es.json`.
* **Listing filters use URL query parameters.** `/properties?operation=&type=&location=&sort=`. The `applyFilters` handler in the page only navigates with non-empty / non-default values, and the canonical URL strips the query string for SEO. Documented in `docs/DATA_MODELS.md` Section 9 and `docs/REBRANDING.md` Section 11.
* **Location matching is case-insensitive and accent-insensitive** (Unicode NFD + combining-mark strip, no external dependency). Implemented in `propertiesService.filter`. Documented in `docs/DATA_MODELS.md` Section 9.
* **Default sorting is stable across SSR and CSR.** Every sort branch uses `id.localeCompare(otherId)` as a tiebreaker so equal-scoring or equal-priced properties render in the same order in both passes. The `ItemList` JSON-LD mirrors the visible order via `position: index + 1`.
* **Mobile filters use an inline collapse, not a modal sheet.** A `< sm` viewport collapses the filter form behind a "Filters" toggle button that reflects the active filter count. The form keeps `method="get" action="/properties"` so it still submits natively without JavaScript.
* **LCP images use `loading="eager"` + `fetchpriority="high"`** (the home hero in `HomeHero.vue` and the property detail cover inside `PropertyGallery.vue`). All other images rely on `<ResponsiveImage>`'s `lazy` / `auto` defaults. The wrapper forwards both attributes to `<NuxtImg>`. Documented in `docs/REBRANDING.md` Section 12.
* **JSON-LD uses stable canonical entity identifiers.** The home page's `RealEstateAgent.@id` is the absolute home URL; the contact page's `ContactPage.mainEntity` and the about page's `AboutPage.mainEntity` reuse the same `@id` so search engines treat the agency as a single knowledge-graph node. Per-listing `RealEstateListing` uses `canonicalUrl` as `@id` when `NUXT_PUBLIC_SITE_URL` is set.
* **Property sample data is validated through Zod** at module load via `propertyListSchema` in `app/features/properties/schemas/property.schema.ts`. A bad record prevents the app from booting — this is intentional.
* **Empty required property strings are rejected by the schema.** `coverImage`, `title`, `slug`, `description`, `location`, `city`, `state`, `country`, `currency`, and every `images[i]` / `amenities[i]` entry are `.min(1)`. The agency config has its own validation in `app/config/agencies/default.agency.ts`.
* **Global stores are reserved for app-wide state only.** `app/stores/` is a `.gitkeep`. The current MVP has no global Pinia store; per-feature stores would live under their feature folder. See `docs/ARCHITECTURE.md` Section 7.
* **`server/routes/` is the right home for Nitro endpoints** (current files: `sitemap.xml.ts`, `robots.txt.ts`). The `app/server/` path does not exist; do not create it.
* **ESLint is auto-resolved by `@nuxt/eslint`.** Do not add a manual ESLint config.
* **Pagination is in v1.0 scope regardless of the placeholder catalog size.** The shipped `app/features/properties/data/properties.ts` is placeholder content for a single template demonstration, not a production agency. The template must be production-ready for any agency on day one. `BasePagination` and the `paginate` utility shipped in M17 are not gated on the placeholder catalog reaching a threshold — the control renders `null` when `totalPages <= 1`, so the current 6-record catalog shows no pagination UI at all. Audit decision recorded in M14.
* **Breadcrumbs are in v1.0 scope for the property detail page only.** Listing pages and top-level pages do not get visible breadcrumbs in v1.0 because they are themselves top-level destinations. The `SeoBreadcrumbs` shared component + `BreadcrumbList` JSON-LD payload shipped in M16 will be reused unchanged by the future `/agents/[id]` and `/developments/[slug]` detail pages — each one only needs a different three-item `items` array. Audit decision recorded in M15.
* **Agency addresses use an optional `AgencyStructuredAddress` companion that drives `PostalAddress` JSON-LD.** The free-text `AgencyContactConfig.address` stays the visible display value (footer + contact card) and is unchanged and required; the optional `structuredAddress` is the schema.org `PostalAddress` payload consumed by the JSON-LD builder on the home, contact and about pages. The three agency `RealEstateAgent` nodes still share the same `toAbsoluteUrl('/')` `@id` so the knowledge-graph node identity is preserved. Property `PostalAddress` is intentionally deferred — the placeholder property catalog has no street addresses or postal codes, and the existing `RealEstateListing` payload documents this as a deliberate omission. Audit and build decisions recorded in M18 and M19.
* **The property gallery uses Swiper v12 (existing dependency) for the main carousel and the preserved custom thumbnail strip.** The first image is the property detail page LCP candidate; the SSR HTML contains it via a `<ClientOnly>` `#fallback` slot as a plain `ResponsiveImage` with `loading="eager"` and `fetchpriority="high"`, and the Swiper replaces it after hydration using the same `src` (browser cache prevents a duplicate download). The first slide inside the Swiper also carries `loading="eager"` and `fetchpriority="high"`; later main images and all thumbnails are `loading="lazy"`. The custom real `<button type="button">` previous and next controls are wired to the Swiper `Navigation` module's `prevEl`/`nextEl` and carry the native `disabled` attribute at the boundaries (no loop, no rewind). Keyboard arrow navigation is enabled only when the carousel is in the viewport. `prefers-reduced-motion: reduce` sets Swiper's transition `speed` to 0 via VueUse's `usePreferredReducedMotion` composable. The fullscreen lightbox is **intentionally deferred** to a future audit: focus trap, body-scroll lock, Escape handler, and backdrop click are not justified by the current placeholder data, and introducing a generic modal system solely for the gallery is out of scope. Audit and build decisions recorded in M20 and M21.
* **Feature services consume data through the data-source adapter boundary.** The v1.1.0 M13 foundation defines the small public surface in `app/core/data-source/`: `DataSourceKind = 'static' | 'api' | 'cms'`, `DataSourceConfig { readonly kind: DataSourceKind }`, `DEFAULT_DATA_SOURCE = Object.freeze({ kind: 'static' })`, `DataSourceAdapter<T> { readonly id, getAll(): readonly T[] }`, the `selectDataSource(config, registry)` selector, and the `DataSourceNotImplementedError` "fail clearly" guarantee. The properties / agents / developments services construct the static adapter at module load (the property service passes `propertyListSchema` as the runtime validation tool — the data file's pre-existing Zod parse at module load is preserved; the agents and developments services pass no schema because no per-feature schema exists yet). The selector is the only place that resolves a `DataSourceConfig` to a `DataSourceAdapter`; a rebrand that flips `DEFAULT_DATA_SOURCE` to a kind with no registered adapter fails loudly at module load. The data files (`app/features/*/data/*.ts`) are unchanged. Audit and build decisions recorded in M13.
* **The property gallery's fullscreen lightbox is a self-contained `PropertyLightbox` component, not a generic `BaseLightbox` shared component.** The v1.1.0 M14 build provides an accessible fullscreen overlay (`role="dialog" aria-modal="true"`, translated `aria-label`, focus trap, body scroll lock, Escape / backdrop / close-button close paths, focus restoration to the opener, prev / next + keyboard arrow navigation, per-slide `alt` text) that reuses the existing Swiper v12 dependency (`A11y` + `Keyboard` modules; `onlyInViewport: false` because the dialog is always in the viewport) for swipe + drag + arrow-key navigation. The lightbox is a sibling of the carousel in the gallery component, not nested inside the Swiper, and is teleported to `<body>` so its `position: fixed` overlay is not clipped by the gallery's `overflow-hidden` container. The carousel's `activeIndex` is the source of truth for the visible counter and the thumbnail `aria-current`; the lightbox opens at the gallery's current slide (via `initialIndex`) and reports navigation back to the parent through the standard `update:activeIndex` emit (Vue 3 parent-child communication goes through the component instance, not the DOM, so the `<Teleport to="body">` rendering does not affect the emit). On close, the gallery calls `swiperRef.value?.slideTo(activeIndex.value, 0)` to snap the carousel's visual position to the last-viewed slide, then restores `activeIndex.value` via `setTimeout(..., 0)` after the Swiper's `update()`-driven `slideChange` event has been dispatched (the `runCallbacks: false` flag only suppresses the `slideChange` from `slideToInternal`, not from `update()`, so the restore is needed). The body scroll lock uses a `useState('property-lightbox-open-count', () => 0)` counter that mutates `document.body.style.overflow` directly, so it composes with the mobile menu's `<html>` `overflow:hidden` (the two target different elements and coexist). Every main image is wrapped in a real `<button type="button">` with a translated `aria-label` and an `mdi:arrow-expand` icon visible on hover / focus-visible, so the open trigger is keyboard-accessible. The lightbox does not change the property data model and does not introduce any new dependency. **No module-level or global state is shared between the gallery and the lightbox** — sync is the standard Vue 3 emit-only contract. Audit and build decisions recorded in M14.
* **The light / dark color mode is a single `<html data-color-mode>` attribute, not a per-component class.** The v1.1.0 M15 build reuses the existing theme-token system: `ThemeConfig` ships an optional `ThemeDarkColors` block that owns only the neutral surfaces, and the CSS serializer (`core/utils/theme-to-css-vars.ts`) emits a light `:root{...}` block and a dark `html[data-color-mode='dark']{...}` block in the same `<style>` tag. The agency's brand colors (`--color-primary`, `--color-accent`, etc.) are declared once on `:root` and inherited by the dark selector, so the agency's identity is preserved across modes by construction. The `useColorMode` composable (`app/composables/useColorMode.ts`) is a `useState` singleton (no module-level or global state) that owns the preference (`'light' | 'dark' | 'system'`), the resolved mode (`'light' | 'dark'`), and the system-preference hint. The composable listens for `prefers-color-scheme` changes via `matchMedia.addEventListener('change', …)` so macOS Auto-Dark at sunset flips the active palette while the user is in `'system'` mode. The `AppThemeToggle` is a real `<button type="button">` whose accessible name (`aria-label`) communicates BOTH the current preference AND the next action for each of the three states in the documented `system → light → dark → system → …` cycle (e.g. "Color mode is light. Switch to dark mode." for the light state). The toggle intentionally omits `aria-pressed` because the cycle is three-state, not binary; the W3C WAI-ARIA `aria-pressed` contract applies only to binary toggle buttons (pressed / not pressed) and would leak a false binary view of the state if applied here. The anti-FOUC inline script in `nuxt.config.ts` runs in `<head>` BEFORE Vue hydrates and sets `<html data-color-mode="...">` based on the persisted cookie and the `prefers-color-scheme` media query, so a returning user never sees a flash of the wrong palette. No new dependencies — the build reuses `@nuxt/icon`, the existing CSS serializer, the existing i18n infrastructure, and the existing token system. No hardcoded dark colors across components — the dark palette is declared once on the theme and consumed through the documented CSS variables. No per-component `dark:` classes — every component reads `var(--color-*)` and the serializer emits the dark block. Audit and build decisions recorded in M15.
* **The minimal multi-tenant foundation resolves the active agency by hostname and ships with exactly one tenant, and the resolver is server-only by code organization.** The v1.1.0 M16 build adds `app/config/agencies/registry.ts` (frozen `agencyRegistry` keyed by tenant id, `DEFAULT_TENANT_ID = 'default'`, the pure `normalizeHostname` + `selectAgencyByHost` resolver, and the `buildEntry` validator that uses the existing `validateAgencyConfig` and pre-resolves the `SiteConfig` so the per-request resolver is a free read), `app/plugins/tenancy.server.ts` (the server-only Nuxt plugin that owns the local `seedSiteConfig(host)` helper — the helper is **not exported** from the plugin file and is therefore not part of the auto-import surface — and calls it with `useRequestURL().hostname` on every Nitro request), and the extracted `buildSiteConfig(agency)` helper in `app/config/site.config.ts`. The registry ships with **exactly one entry** — the default tenant — and an empty `hosts` list; every unknown hostname resolves to it via the fallback, so the current single-agency behavior is preserved verbatim. The resolver is intentionally minimal: port stripping at the first `:`, whitespace trimming, lowercasing; IPv6 / IDN / IDNA normalization is a documented future concern (a rebrand that owns an IPv6 literal or an IDN domain lists it explicitly in the entry's `hosts` array). Per-request isolation comes from Nuxt's `useState` (per-request on the server, payload-replicated to the client); the `.server.ts` suffix on the plugin restricts it to the Nitro bundle so the client never re-resolves. **Client-safe composable.** `app/composables/useSiteConfig.ts` is the only file every component imports to read the active agency + theme; the composable does **not** import the registry, the resolver, or the seed function — it only reads the request-seeded `useState('site-config')` (with the `siteConfig` initializer as a documented fallback for unit tests). The boundary is enforced by a 7-case Vitest suite in `app/composables/useSiteConfig.test.ts` that pins the textual absence of every registry identifier (`agencyRegistry`, `selectAgencyByHost`, `DEFAULT_TENANT_ID`, `normalizeHostname`, the registry import path, the `seedSiteConfig` export, and three alternative spellings — `seedTenant`, `resolveAndSeed`, `initFromHost`) plus the runtime module-exports shape (`Object.keys(mod).sort() === ['useSiteConfig']`). A future regression that re-adds `seedSiteConfig` to the composable, or imports the registry, fails both checks. **No** auth, **no** billing, **no** database, **no** admin, **no** dynamic tenant creation, **no** per-tenant i18n / currency / theme / `NUXT_PUBLIC_SITE_URL` overrides (those are independent post-M16 follow-ups documented in Section 6). Adding a tenant is a one-entry change to `agencyRegistry` — `acme: buildEntry(acmeAgencyConfig, ['acme.example.com', 'www.acme.example.com'])` — with no service, page, or component changes. Audit and build decisions recorded in M16.
* **The data-source contract is async-first with a synchronous accessor, the static and api adapters both satisfy it, and the api source for properties is server-only by code organization with a same-origin Nitro endpoint as the data-flow mechanism between SSR, hydration, and client-side navigation.** The v1.1.0 M17 build grows `DataSourceAdapter<T>` from `getAll(): readonly T[]` to two surfaces: a primary async `loadAll(): Promise<readonly T[]>` and a synchronous `getAll(): readonly T[]` accessor. The static adapter pre-loads at construction so `getAll()` works synchronously without awaiting `loadAll()`; the api adapter populates the cache after the first `loadAll()` resolves and throws on `getAll()` until then. The service layer treats `loadAll()` as the only contract entry point and ignores `getAll()` — the data is the resolved `loadAll()` value, passed to every pure service helper. Pages consume `loadAll()` through Nuxt's `useAsyncData('key', () => service.loadAll())` so SSR awaits the load before rendering; the SSR markup carries the resolved value to the client payload and client hydration reuses it. **Data flow (server → client → client-side navigation).** The property data is owned by a server-only property loader at `server/utils/properties.ts` (the canonical Nuxt 4 location for server-only utilities — the file is bundled to the Nitro server output only, never to the client). The loader reads `NUXT_PROPERTIES_DATA_SOURCE` and, when the kind is `'api'`, constructs the api adapter via `createApiDataSource` (which uses the platform `fetch`, validates the response against `propertyListSchema`, and maps failures to the four documented error classes), then eagerly fetches the remote property list. When the kind is anything else the loader returns the bundled static adapter. **No permanent process-lifetime cache is retained for successful API results.** Each call to `loadPropertiesServer()` constructs a fresh adapter (api or static, driven by `NUXT_PROPERTIES_DATA_SOURCE`) and awaits its `loadAll()`; a later request observes the latest upstream data, not a stale snapshot. Concurrent in-flight calls share a single fetch via an in-flight `pending` promise that is cleared on settle (success or failure), so the next call performs a new fetch. The api is therefore fetched on every call, not "at most once per server lifetime". The loader exposes the resolved list through a single function, `loadPropertiesServer()`, which is consumed by two surfaces: (1) the same-origin Nitro endpoint at `server/api/properties.get.ts`, which the app-side property service calls via `$fetch('/api/properties')` (loopback on the server, same-origin HTTP on the client); (2) the sitemap at `server/routes/sitemap.xml.ts`, which imports the loader directly — the sitemap is a Nitro server route and must not import the app-side property service (a client-bundled module that depends on the Nuxt app context). Routes that do not need properties (`/about`, `/contact`, `/agents/*`, `/developments/*`) do not call `propertiesService.loadAll()` and do not trigger the api fetch; the loader is invoked only by the home, listing, and detail pages, and by the sitemap. **Cross-cutting boundary.** The api-adapter module and the three `NUXT_PROPERTIES_*` env-var name strings are imported and read exclusively by `server/utils/properties.ts`. The property service is bundled to both server and client; it references only the same-origin path `/api/properties` (no external api URL, no env-var name string, no api-adapter import). The boundary regression test in `app/features/properties/services/properties.service.boundary.test.ts` pins the contract: a textual scan of the service file fails the suite if any of the api-adapter import, the env-var name strings, the data-source contract runtime exports, a `process.env` reference, the `typeof window === 'undefined'` guard, or the server-only plugin / loader paths ever reappear in the runtime code. The loader tests in `server/utils/properties.test.ts`, the endpoint tests in `server/api/properties.get.test.ts`, and the sitemap tests in `server/routes/sitemap.xml.test.ts` pin the server-side contract. **Four error classes.** `DataSourceMissingConfigError` (kind + missing field name — raised by the api adapter at construction on empty / whitespace endpoint, or by the server-only loader at `server/utils/properties.ts` when `NUXT_PROPERTIES_DATA_SOURCE=api` but `NUXT_PROPERTIES_API_URL` is empty); `DataSourceHttpError` (non-2xx response — carries the status code and endpoint URL, no response body); `DataSourceTimeoutError` (request exceeded the configured timeout — carries the endpoint URL and the `timeoutMs`; the original `AbortError` is intentionally NOT chained on the public error); `DataSourceInvalidPayloadError` (2xx response that fails Zod validation — carries the endpoint URL and the underlying `ZodError` as `cause`). **HTTP API adapter.** `app/core/data-source/adapters/api-adapter.ts` ships `createApiDataSource<T>({ endpoint, schema?, source?, timeoutMs?, fetchImpl? })` — uses the platform `fetch` (no new dependencies), validates the endpoint at construction, wraps every request in an `AbortController` with a configurable timeout (default 10 000 ms; timer cleared on both success and failure so the request does not leak), sends an `Accept: application/json` header, runs `schema.safeParse(json)` after parsing the JSON when a schema is supplied, accepts any array-shaped JSON when no schema is supplied (non-array bodies still raise `DataSourceInvalidPayloadError`), re-throws other fetch errors as-is, and memoises the resolved array per-instance (repeated `loadAll()` calls share the same fetch; the `pending` memo also coalesces concurrent calls into a single fetch).
